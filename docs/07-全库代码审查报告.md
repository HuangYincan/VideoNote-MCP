### 4.2 P2 开放项

| 编号 | 问题与证据 | 影响 | 当前状态与后续 |
|------|------------|------|----------------|
| P2-01 | **yt-dlp 内部 egress SSRF 未完全闭合**。应用入口和部分下载器已做 URL/逐跳公网校验，但 `app/downloaders/generic_downloader.py:82-83`、`app/downloaders/youtube_downloader.py:181-182,248-249`、`app/services/inspect.py:256-257` 仍把 URL 交给 yt-dlp extractor；extractor 的重定向、HLS manifest、分片或最终媒体资源可能在应用层校验之后再发起请求。 | 恶意或被篡改的 extractor 资源可能令服务端访问内网、回环或云元数据地址；仅校验初始 URL 不能证明所有内部请求安全。 | **开放**。需要 yt-dlp 网络适配/请求钩子，或部署层 egress 白名单、网络隔离与元数据保护。未在本轮声称彻底解决。 |
| P2-02 | **manifest 清理存在 TOCTOU**。当前 `app/utils/task_manifest.py` 用进程内 `_MANIFEST_LOCK`（`threading.RLock`）串行化同一进程的 manifest 读-改-写，并在清理前做 `resolve()` 检查；但检查与删除之间，在不可信共享文件系统上仍可被**另一进程**替换符号链接。 | 若任务数据目录被低权限/不可信主体同时控制，理论上可能把清理操作导向检查时未指向的目标；进程内并发写入已收口，但跨进程竞态仍在。 | **开放 P2**。当前实现适用于受信任的本机数据目录；如需支持共享不可信目录，应改用目录 fd、`openat`/`unlinkat`、no-follow 与 owner/inode 校验等平台相关方案。 |
| P2-03 | **stderr 日志文件路径安全仍非 no-follow 模型**。`videonote_mcp/server.py:58-76` 使用普通 `exists()`/`stat()`/`replace()`/`open()`，尚未完成 symlink、owner、权限和替换竞态校验。 | 被控制的数据目录可能诱导日志轮转或追加写入到非预期文件，造成日志篡改、敏感错误信息外泄或权限问题。 | **开放**。应在明确支持的 Unix/Windows 部署模型下补充安全创建、`O_NOFOLLOW`（可用时）、owner/mode 校验和原子轮转；失败时宁可保留原始 stderr。 |

### 4.3 P3/治理与优化候选

以下项目不构成当前发布阻断，但应登记并按产品、部署或性能预算安排：

| 编号 | 候选 | 说明 |
|------|------|------|
| P3-01 | batch 队列背压 | `batch_generate_notes` 单次最多 50 条，但 batch 使用线程池排队并绕过普通 admission；多个 batch 并发调用仍可能堆积。后续可增加全局 batch 配额、队列长度和拒绝/取消策略。 |
| P3-02 | FastMCP 同步工具占事件循环 | `inspect_video`、batch 以及 `process_media` 的部分重操作仍是同步工具；改为 `anyio.to_thread` 需要同步调整 MCP 注册面和直接调用契约测试。 |
| P3-03 | `pyannote.audio` 兼容矩阵 | `pyannote.audio>=3.1` 缺少主版本上界；说话人分离是可选重依赖，应建立 Python/torch/torchaudio/pyannote 兼容 CI 后再钉版本。 |
| P3-04 | note cache 生命周期 | 转写/媒体缓存目前缺少 TTL、LRU 或容量上限；长期运行可能持续增长。 |
| P3-05 | 截图与 ffmpeg 粒度 | 每个 timestamp 独立启动 ffmpeg，长视频截图时进程启动成本较高；可评估批量抽帧或单进程管道。 |
| P3-06 | 内存峰值 | 抽帧、拼图和 base64 编码会同时持有多份图像数据；超长视频或高分辨率设置需要峰值预算/限额。 |
| P3-07 | 大文件校验成本 | manifest/产物校验涉及 SHA-256 时会扫描大文件；可按场景区分控制文件与媒体文件校验策略。 |
| P3-08 | 打包与运行镜像漂移 | `Dockerfile` 当前未单独复制源码树下的 `skills/`，虽 wheel include `skills/**`；应保留 wheel 内容门禁，并验证源码运行与镜像运行两条路径。 |
| P3-09 | 转写器选择项漂移 | Whisper CLI 的 choices 与 registry/实际可用模型可能分叉；应从单一 registry 生成 schema、CLI 提示和测试。 |
| P3-10 | 依赖供应链可复现性 | Docker/Actions/apt/pip/可选依赖/插件仍有可变引用；应在不破坏升级策略的前提下补 digest、lock 或定期更新流程。 |
| P3-11 | Fernet key 信任模型 | `fernet.key` 已使用 0600 与并发安全创建，但 owner、已有 symlink 和配置目录信任仍可进一步加强。 |
| P3-12 | CLI export 输出目录 | CLI 的 `export --out-dir` 保留本机用户显式导出到桌面的能力，未复用 MCP 数据目录门禁；是否收紧取决于 CLI 与 MCP 的威胁模型。 |

## 5. 本轮已修复问题

### 5.1 任务状态、提交与成功发布

- `videonote_mcp/server.py:268-341`：`_write_status()` 先原子写 `status.json`，成功后才同步 SQLite；普通状态写失败保留兼容的快照回退，关键发布使用 `strict=True` 重新抛错。
- `server.py:482-572`：MCP worker 调用 `NoteGenerator.generate(..., publish_success=False)`；固定发布顺序为 `result.json → manifest → SUCCESS`。自动导出产物也在最终 manifest 中登记，避免轮询看到 SUCCESS 却拿不到结果。
- `server.py:663-756`：普通任务的 admission、线程池 submit、Future/Event 登记处于同一把 `_tasks_lock` 内；普通任务预占名额覆盖排队和执行，batch 通过 thread-local bypass 不占普通 admission 但仍由线程池排队。提交失败会回滚内存注册表、任务目录、manifest 和全局 `video_tasks` 索引；回滚清理若不完整，以结构化诊断附加到原始异常，不替换原始提交错误。
- `server.py:1194-1290`：非 dict 或损坏状态不会伪装成 `PENDING`；无可用快照时返回 `UNKNOWN`，提升终态可观测性。

### 5.2 取消、缓存与媒体处理

- `app/services/note.py`、`app/services/pipeline.py`、`app/downloaders/`、`app/transcriber/audio_preprocess.py`、`app/utils/video_reader.py` 与 `app/services/diarization.py`：取消事件贯穿平台字幕、音频/视频下载、ASR、预处理、ffmpeg、帧抽取、说话人分离和后处理边界；可控的 ffmpeg/流式下载子进程会 terminate/kill 收尾，`TaskCancelledError` 不再被通用异常/fallback 吞掉。第三方网络、模型推理或 SDK 的阻塞调用无法被线程外硬中断；B 站弹幕/评论聚合 helper 仍不接收 `cancel_event`，取消可能要等它返回后才在下一边界生效。
- 视频抽音频使用同目录临时文件，只有完整 ffmpeg 成功后才 `replace()` 到最终路径；取消、超时或失败不会覆盖已有完整缓存，也不留下最终半成品。
- `_save_metadata()` 的索引写入失败会重新抛出，避免文件产物已存在但任务错误地发布 SUCCESS。

### 5.3 SQLite schema 与 DAO 一致性

- `app/db/engine.py:50-64`：每个 SQLite 连接开启 `PRAGMA foreign_keys=ON`；保留既有数据库文件权限收紧。
- `app/db/init_db.py`：兼容迁移仅在 SQLite 上执行；`_migrate_video_tasks` 对缺失的 `video_tasks` 表安全 no-op（新库先由 `create_all` 建表），重复迁移保持幂等。迁移异常不再被当成旧库可继续运行，而是记录并 re-raise。
- `app/db/models/models.py`、`app/db/model_dao.py`、`app/db/provider_dao.py`、`app/db/video_task_dao.py`：ORM 与写入入口要求 provider 一致；api_key 加密失败中止整笔更新；DAO 写失败 rollback 后重新抛出，索引写入失败不会再静默假成功。

### 5.4 加密、manifest 与 ffprobe

- `videonote_mcp/crypto.py:29-147`：新增 `EncryptionError`；Fernet key 创建、读取或加密失败均 fail-closed，不再回退明文；`encrypt_status()` 以 `fernet`/`encryption-error` 暴露当前进程状态。
- `app/utils/task_manifest.py`：`record_task_paths(strict=True)` 写入后回读校验，关键 manifest 失败会阻断 SUCCESS；新增模块级 `threading.RLock` 串行化同一进程内 manifest 读-改-写与删除。现有清理仍对目标做 `resolve()` 数据根校验，但跨进程检查—删除 TOCTOU 仍是开放 P2，仅适用于受信任的本机数据目录。
- `app/utils/video_reader.py`：移除无 timeout 的 `ffmpeg.probe`，改用严格的带 120 秒 timeout 的 ffprobe，并拒绝 NaN、Inf、负数时长；`audio_preprocess.probe_duration` 仍是 best-effort，失败返回 0，分块路径由 `chunk_duration_guess` 回退 1800 秒并记录 warning。

## 6. 文档/契约同步

本报告以 #148 的历史登记为基础，并补充当前 #149：历史登记项为 **docs/05 #149**、执行批次为 **docs/06 批 40**；#148 的执行批次/变更记录仍保留在原文档中。当前用户契约为：

- 普通 `generate_note` / `prepare_note_material` 在提交锁内预占 `VIDEONOTE_MAX_WORKERS` admission 名额，预占覆盖排队与执行；超限拒绝；
- `batch_generate_notes` 单次最多提交 50 条，明确旁路普通 admission，逐条交给线程池排队；不建议并发调用多个 batch，以免队列堆积；
- `task(action="cancel")` 对异步笔记/素材任务只做协作式取消：事件沿字幕、下载、ASR、预处理、ffmpeg、抽帧、说话人分离和后处理传播，但第三方阻塞调用无法硬中断；B 站弹幕/评论 helper 不接收 `cancel_event`；
- `process_media` 仍为同步工具，不登记任务注册表，没有可由 `task(action="cancel")` 控制的后台 task；
- 任务只有在 `result.json` 与最终 manifest 持久化成功后才发布 `SUCCESS`；提交失败的回滚诊断不覆盖原始错误；DAO 写失败 rollback/re-raise；
- SQLite 迁移只处理 SQLite；缺失 `video_tasks` 表的迁移 helper 安全 no-op，迁移失败 re-raise；
- 任务 `manifest` 的 RLock 只保证同一进程内读-改-写串行，跨进程检查—删除 TOCTOU 仍为 P2；
- `task(task_id)` 看到 `SUCCESS` 时可依约读取结果；若状态文件损坏且没有可信内存快照，则返回 `UNKNOWN`，不应无限轮询。

## 8. 结论与维护建议

当前 `dev` 已包含 #149 实现；#148 的完整验证基线仍为 948 passed，本次 #149 记录以 focused validation 为准，未在文档回填阶段声称重新通过全量套件。核心任务正确性和敏感信息 fail-closed 已补齐；合并前建议由维护者重点确认三件事：

1. 部署环境是否把数据目录视为受信任本机目录；若不是，优先处理 P2-02/P2-03；
2. 是否需要对 yt-dlp 的 extractor/媒体资源实施部署级 egress 隔离；若需要，按 P2-01 建立集成验证，不要仅依赖入口 URL 校验；
3. 是否接受 batch 旁路普通 admission 的队列语义；若不接受，设计带背压的统一全局队列后再改文档和实现。

本报告不替代发布前的真实环境演练；在启用可选转写、Docker、外部 egress 或共享文件系统时，应按对应部署模型补充专项测试。
